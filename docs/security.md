# Security

## What the App Does

- It stores and edits nicknames/identifiers.
- It encodes/decodes the Ledger Passwords metadata block.
- It transfers that block to or from the Ledger after physical approval.

## What the App Does Not Do

- It never asks for the recovery phrase.
- It never derives final passwords.
- It never displays final passwords.
- It does not replace the Ledger as the root of trust.
- It does not sync automatically to the cloud.

## Sensitive Data

Nicknames are not cryptographic secrets, but they may reveal services in use: `bank`, `gmail`, `github`, and so on.

Recommended handling:

- private local storage;
- export only through explicit user action;
- no production logs containing nicknames;
- no telemetry;
- no network;
- automatic local backup before writing to the Ledger.

## Main Risks

### Bad Rename

Renaming a nickname changes the password generated by the Ledger.

Mitigation:

- visible warning in the UI;
- diff before push;
- confirmation before writing.

### Accidental Ledger Overwrite

Mitigation:

- automatic local backup before push;
- device-vs-local diff;
- Android/CLI confirmation;
- physical Ledger approval;
- verification by dump after writing.

### Corrupted Backup

Mitigation:

- strict validation;
- tolerant parsing but strict export;
- corruption display;
- push refusal on blocking corruption.

### Compromised Phone

The phone could modify nicknames and push a bad list if the user approves on the Ledger.

Reasonable mitigation:

- readable diff;
- no automatic sync mode;
- display of the number of modified entries;
- recoverable backup.

## Android Permissions

MVP:

- USB host;
- file access only through the Storage Access Framework and only on user action.

No network permission in V1.
